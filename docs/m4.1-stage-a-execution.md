## 3. Gate failure

**Expected Store app name:** `za-pos-m4-store-a`

**Actual Store app name:** `za-pos-m4-staging-client-m4-store-a`

This is an explicit abort condition in `docs/m4.1-live-integration-plan.md`.
Execution stopped before adding the Store UUID to `VULA_ALLOWED_APP_UUIDS`.
The CP allowlist remains empty, so the release controller will not modify the
Store through an existing-app path.

### Root cause

In the deployed commit `9ae7fc5`:

- `orchestrateClientDeployment()` omits `deploymentName` from the
  `store_deploy_*` step metadata.
- `runJobSteps()` omits `deploymentName` when it creates the Store row.
- Therefore `stores.deployment_name` is null, and the provisioning path falls
  back to ``${company.slug}-${store.name}``:
  `m4-staging-client` + `M4 Store A` → `m4-staging-client-m4-store-a`;
  the Store app name becomes `za-pos-m4-staging-client-m4-store-a`.

The staging guard correctly enforced the approved project/server/destination,
name prefix and domain pattern, but its name check is a prefix check; it did not
force the exact expected name. The plan's exact-name acceptance gate caught the
difference.

### Recommended correction

Add `deploymentName` to the onboarding step metadata and pass it through
`createStore`, with a regression test asserting the exact app name. Then
redeploy the staging CP from a new reviewed commit and recreate the disposable
Store. Do not rename the live app or edit its registry row by hand.
