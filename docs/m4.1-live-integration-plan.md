## 2. Coolify credential scope — verified residual access

This was checked read-only against the installed **Coolify 4.4.7** on
2026-10-22. No credential value was printed.

### 2.1 What the API supports

- API tokens are **team-bound**, not project- or application-scoped. The token's
  `team_id` determines the resources it can see.
- Token abilities are `read`, `read:sensitive`, `write`, `write:sensitive`,
  `deploy` and `root`; a `root` token bypasses ability checks.
- The installed Coolify's only team is **Root Team (`id: 0`)**. The existing CP
  token can list the whole Root Team: **28 applications, 13 projects and one
  server** were visible in the read-only probe.
- **No dedicated staging token exists yet.** The CP `.env` token is the existing
  Root Team credential; its abilities are not exposed by an API endpoint, and it
  is used for writes/deploys by the CP, so it must be treated as read/write/
  deploy-capable. It must not be reused for staging.
- There is no per-project token or per-application token in this version. A new
  team cannot use the existing server without adding a separate server resource
  to that team; the only server is owned by Root Team. A genuinely isolated
  team would therefore require a separate Coolify instance/server, which is
  outside Stage A.

### 2.2 Staging token rule

The existing CP token must **not** be reused for staging. Stage A must create a
dedicated Coolify user/token named for M4 staging, with only `read`, `write` and
`deploy` — no `root`, no `read:sensitive`, and no `write:sensitive` unless a
verified operation requires it. Record the token ID and user ID (never the token
value), set a short expiry, and revoke both at cleanup.

Even with least abilities, the token remains **broad within Root Team**. It can
update, deploy and delete unrelated Root Team applications. `VULA_ALLOWED_APP_UUIDS`
is a Control Plane code-level guard for release operations; it is **not**
Coolify permission scoping and cannot limit what a leaked token can do.

**Approval condition:** Stage A requires explicit acceptance of this residual
broad access, or a separate Coolify instance/team-owned server. Without that,
Stage A cannot honestly be described as least-privilege and remains blocked.

## 3. HTTPS, DNS and certificate arrangement

The hostnames are already covered by the existing wildcard DNS:

- `*.vula-app.co.za` resolves to `145.241.101.1`; random unclaimed subdomains
  resolve there too.
- `m4-cp.vula-app.co.za` and `m4-store-a.vula-app.co.za` resolve to that address
  and currently return the Traefik default certificate because no router exists
  yet. That is expected before app creation; it is not a valid serving
  certificate.
- Existing applications (`staging-cp.vula-app.co.za`,
  `demo-general.vula-app.co.za`) present per-host Let's Encrypt certificates.
  There is no wildcard certificate. Port 80 answers with a 307 redirect to
  HTTPS, and existing issuances show the HTTP-01 challenge path works.
- After the CP and Store apps are created, Traefik must obtain a per-host Let's
  Encrypt certificate. Acceptance requires the certificate SAN to exactly equal
  the hostname and the issuer to be Let's Encrypt, not `TRAEFIK DEFAULT CERT`.
- **No Cloudflare Tunnel, no new DNS record, no DNS provider change, no shared
  proxy/Traefik change and no `acme.json` action are permitted.** If issuance
  fails, stop and report; do not weaken HTTPS or introduce a tunnel.

The exact URLs for Stage A are therefore:

```text
Control Plane: https://m4-cp.vula-app.co.za
Store A:       https://m4-store-a.vula-app.co.za
```

## 4. Persistent volume and registry contract

The CP image sets:

```dockerfile
ENV CP_DB_PATH=/data/control-plane.db
VOLUME /data
```

and the entrypoint creates/chowns the `CP_DB_PATH` directory before starting as
`node`. Stage A therefore mounts the **new** volume
`vula-cp-m4-staging-data` at `/data` and sets `CP_DB_PATH=/data/control-plane.db`.
The volume root and the DB directory are the same path.

The volume is newly created for this stage and is never copied from the
production CP. Before the Store is onboarded, the staging CP must report zero
stores, zero clients/panels and zero releases. Any pre-existing registry row is
an abort condition. `DB_PATH` must not be set to a production path; only
`CP_DB_PATH` is used.

The tenant's `/data` is a separate volume (`vula-store-m4-store-a-sqlite-db`),
not the CP volume or the CP database directory.

## 6. Abort conditions

Abort immediately and leave the test apps stopped (do not delete source data) if:

- the Root Team token residual is not explicitly accepted, or the staging token
  has `root`/`read:sensitive` abilities or cannot be identified;
- the CP is using a production registry DB, production JWT/licence key,
  production office credentials or a production Coolify token;
- the CP app is built from a dirty `dev` tree or a commit other than the
  reviewed branch commit;
- the CP volume is not new/empty, or `CP_DB_PATH` is outside the mounted volume;
- either proposed hostname returns the Traefik default certificate after the
  issuance window, or any DNS/proxy/tunnel change would be needed;
- the CP registry contains any production, demo or super-stores row, or the
  allowlist contains any UUID other than `za-pos-m4-store-a`;
- `za-pos-m4-store-a` already exists before onboarding, or the CP creates a
  different app/volume/path than §A3;
- the running digest differs from the approved Store A digest, or the registry
  manifest is not `linux/arm64`;
- `/health` does not report the exact version/revision, or the database is not
  connected;
- more than one `/data` storage, app, domain or container could serve the Store;
- a Coolify deployment is active/non-terminal or reports failed/cancelled;
- registry authentication, image pull or deployment UUID retrieval fails.

A failed Stage A does not proceed to Stage B.

## 7. Stop-first recovery

Use this after a failed pull, failed health check, failed deploy or a CP crash.
The invariant is **one container per SQLite volume**.

1. **Do not start a second container manually.** Leave the Store stopped. Do not
   run `docker start` or trigger another Coolify deploy while the failed/new
   container exists.
2. **Inspect CP records read-only:** tenant `release_state`,
   `desired_release_id`, `last_release_id`, `previous_release_id`,
   `deploy_status`, deployment lock and deployment history.
3. **Reconcile Coolify before retry.** Read the tracked deployment UUID or the
   application's latest deployment. A queued/in-progress job means wait. Only a
   terminal failed/finished job permits recovery.
4. **Confirm no live container remains** through application status and, where
   available, the host container list. If status is absent or still running,
   abort; do not patch or start.
5. **Choose the last-known-good release** by exact digest/version/revision and
   schema range. Never use a mutable tag.
6. **Check the database schema.** If the current schema is outside the target
   release's supported range, restore a verified pre-change test DB copy; never
   initialise an empty replacement DB for an existing tenant.
7. **Recover through the CP rollback path** (stop/confirm stopped → exact image
   → trigger → terminal Coolify status → health version/revision). Do not bypass
   the schema gate.
8. **Verify** exactly one container, one `/data` volume, DB identity/integrity,
   schema and expected data. Record the audit rows.
9. **CP crash:** wait for the lock to expire only as a last resort; reconcile the
   running deployment first. A stale `running` row with no active Coolify job is
   marked failed before retry. Never delete a lock while a Coolify deployment is
   active.
10. **Failed pull/registry auth:** keep stopped, fix the staging registry
    credential, retry the same digest. Do not switch to a Dockerfile build.
