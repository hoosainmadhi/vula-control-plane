`VULA_ALLOWED_APP_UUIDS` is the authoritative modification boundary. In
production the Control Plane refuses existing-app changes if the list is empty.
Newly provisioned app UUIDs must be added before their first upgrade.

The published arm64 release provides only **one** immutable image per kind:

- Store A: `ghcr.io/hoosainmadhi/vula-pos-store@sha256:6db6b974b78c663a42796db9b738cc4ee21bc097bd1f9ba29ea836ef8ef5cb14`
  (`v2026.10.21-5781c2c`, revision `5781c2c0a891f896b12e2f6cfdc7d7678cc18fa3`, schema 1/1/1).
- HO A: `ghcr.io/hoosainmadhi/vula-pos-ho@sha256:d50f979c3c7a9f1dfdd51928cecf9f29ca6fd01f7dbfb594905b5c34ecb6a9d6`
  (same version/revision/schema 1/1/1).

The amd64 digests (`4687b383…`, `243d9727…`) are not deployable on this host
and must not be used.

To test an actual upgrade and rollback, a **second approved arm64 digest per
kind** is required. Proposed, not executed:

- build the same reviewed source commit `5781c2c` for `linux/arm64` with a
  distinct `VERSION`, e.g. `v2026.10.21-5781c2c-m4b`, and the same `GIT_SHA`;
- publish only to a **private staging registry/location** (or a private staging
  tag approved for M4.1), never to the production release tag;
- record the exact store/HO digests, architecture, version and revision;
- register release B as `beta` in the staging Control Plane only.

If that publication is not approved, M4.1 may run provisioning, dedup, lock,
schema-refusal and dry-run tests with A, but **must not claim an upgrade or
rollback was tested**. The upgrade/rollback steps abort.

## 4. Read-only Coolify contract evidence (2026-10-22)

Checked against the installed Coolify 4.4.7 with GET requests only; no credential
values were printed:

- `GET /api/v1/version` answered; probe reports **4.4.7**.
- `GET /applications/{uuid}` for the store and HO returns
  `status: "running:healthy"`, `build_pack: "dockerfile"`, `environment_id`,
  `destination_id`; `docker_registry_image_name/tag` are `null` for these
  Dockerfile apps. The image fields were therefore confirmed as nullable fields,
  not yet validated on a live Docker Image app.
- `GET /applications/{uuid}/storages` returns
  `persistent_storages: [{ mount_path: "/data", name: … }]`, `file_storages: []`.
- `GET /deployments/applications/{uuid}` returns deployment records with
  `deployment_uuid`, `status: "finished"`, `created_at`, `finished_at`.
- `GET /deployments/{uuid}` returns the same record for the latest deployment.
- Read-only source inspection of `StopApplication` shows the stop API queues an
  async job, removes the stopped containers and writes application status
  `exited`; the API response is `"Application stopping request queued."`. The
  Control Plane therefore polls application status and must not treat the stop
  API response as proof. **Live stop semantics remain to be exercised on an
  isolated test app in M4.1**, not during this read-only pass.

## 5. Execution sequence after approval

1. Create the dedicated staging Coolify team/token and project, or configure the
   equivalent project-scoped token.
2. Deploy `vula-cp-m4-staging` with the isolated registry DB and staging-only
   secrets; verify `/health` and that its registry has no production rows.
3. Create the three test apps from digest A, with test-only env and test data
   volumes. Record their UUIDs; add exactly those UUIDs to the allowlist; restart
   the staging CP so the allowlist is active.
4. Verify exact digests, arm64, `/data` storage, tenant identity, version/
   revision health, and that no production/demo app is selected.
5. Run provisioning, idempotency, concurrent request, expired-lock, schema
   refusal, missing-storage and allowlist-refusal checks.
6. If release B is approved and published: upgrade A→B, verify Coolify status
   transitions and health version, then rollback B→A with the same checks.
7. Run the two-store, two-wave test with `stopOnFailure=true`; fail wave 1 and
   confirm wave 2 is skipped.
8. Capture redacted evidence: batch/item/deployment/audit rows, Coolify
   deployment statuses, timings, image digests and health revisions. No tokens,
   passwords, private keys or tenant secrets.

## 6. Abort conditions

Abort immediately and leave test apps stopped (do not delete source data) if:

- the CP is using a production/registry DB, production JWT/licence key or
  production office credentials;
- any production, super-stores or demo UUID appears in the allowlist or target
  selection;
- an app name is not a `vula-m4-*` test app;
- `/data` storage is missing, the tenant identity does not match, or the schema
  is unknown/incompatible;
- a Coolify deployment is active or non-terminal, returns failed/cancelled, or
  the new `/health` version/revision does not match the release;
- stop is not confirmed or two containers could mount the same SQLite volume;
- registry authentication, image pull or deployment UUID retrieval fails;
- a staging release is not the exact approved digest or architecture.

A failed pilot wave stops later waves; no retry against an active deployment.

## 7. Cleanup

1. Stop/delete `vula-m4-store-a`, `vula-m4-store-b`, `vula-m4-ho` and their
   volumes; delete the `vula-m4-staging` project.
2. Delete the staging CP app/project/volume and `/data/m4-staging`.
3. Remove `/data/apps/vula-m4-staging`.
4. Revoke the staging Coolify token and staging registry credential.
5. Remove any staging-only release-B images if approved and no longer needed.
6. Preserve redacted logs/evidence and confirm the original store/HO apps,
   volumes, databases, domains and deployments are unchanged.
7. No production registry, production CP database, `acme.json`, proxy, DNS or
   firewall change is part of cleanup.
