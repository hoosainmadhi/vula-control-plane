# M4.1 Coolify Token Rotation Plan

**Status:** prepared, **not executed**. No token was generated, copied, revoked or
rotated. OptiMed is strictly out of scope for Vula M4.1; any OptiMed restart,
redeploy or environment change needs separate approval.

## 1. Why this is coordinated, not a Vula-only change

The exposed Root Team Coolify API token is used by both:

| Consumer | Evidence | What breaks without a valid token |
| --- | --- | --- |
| Vula Control Plane runtime | `/home/hoosain/apps/za-pos-control-plane/.env` contains the exact exposed value; `src/services/coolify.ts` reads `COOLIFY_API_TOKEN` | Provisioning, redeploy, release apply/rollback, wave rollouts |
| Vula deployed Control Plane(s) | Coolify apps `vula-cp-prod` and `vula-cp-staging` expose a `COOLIFY_API_TOKEN` env key (values masked by the API) | Their Coolify-backed lifecycle actions |
| OptiMed Control Plane runtime | `/home/hoosain/apps/optimed-control-plane/.env` contains the exact exposed value; `src/services/coolify.ts` reads `COOLIFY_API_TOKEN` | Practice provisioning, deploy, restart, stop/start, domain reassignment and teardown |
| OptiMed deployed Control Plane | Coolify app `optimed-control-plane` exposes a `COOLIFY_API_TOKEN` env key (value masked by the API) | Same OptiMed platform operations |
| Vula release script | `za-pos-control-plane/scripts/release-apps.sh` falls back to the OptiMed `.env` when its own env is unset | `release-apps.sh fleet/cp/all/<name>` cannot deploy |
| Coolify probes | Both control planes' `scripts/coolify-probe.ts` | Connectivity checks report failure |

The audit searched the entire `/home/hoosain/apps` tree, shell history,
user/system systemd units and cron. Only the two `.env` files contained the exact
exposed value. No local running process, local Docker container, cron entry or
systemd unit contains it. The repository's CI has no workflow that references the
token, and the isolated M4 branch has no `.github` directory.

Deployed app environment values are masked by the API. We therefore treat both
deployed control planes as consumers even though their exact current value cannot
be proven read-only.

## 2. OptiMed dependency and boundary

OptiMed is a **direct consumer** of the exposed token. Revoking it without a
coordinated replacement would break OptiMed's platform lifecycle routes:
`POST /practices/:id/deploy`, subscription stop/start, domain reassignment,
practice provisioning and `DELETE /practices/:id` teardown.

## 3. Replacement design

Create two new tokens, not one shared token:

1. **`vula-m4-staging`** — only for the isolated Stage A Control Plane. Abilities:
   `read`, `write`, `deploy`; no `root`, no sensitive abilities. Short expiry.
   Its scope is still the Root Team; the Stage A creation guard and UUID
   allowlist are the application-level boundaries.
2. **`legacy-cp-replacement`** — for the existing Vula Control Planes, OptiMed
   Control Plane and release script. Abilities: `read`, `write`, `deploy`; no
   `root`, no sensitive abilities. This still has Root Team visibility because
   Coolify 4.4.7 has no project/app token scope.

Do not reuse the exposed token for either. Do not put either value in a
repository, report, terminal history or command line. Store them only in the
approved secret store and the Coolify/OptiMed environment update path.

## 4. Exact replacement and verification sequence

This sequence requires separate approval. It does not start until approved.

### Phase 0 — freeze and evidence

1. Record current Vula and OptiMed health, Coolify app statuses, token consumer
   list and token IDs (never values).
2. Confirm no deployments are queued or running in Coolify.
3. Confirm Stage A is not deploying and no release batch is active.
4. Keep the exposed old token valid until Phase 4 completes; do not revoke yet.

### Phase 1 — create and verify the replacement

1. Create `vula-m4-staging` and `legacy-cp-replacement` in Coolify with the
   abilities above and a bounded expiry. Record token IDs, owner, abilities and
   expiry in the ownership manifest/secret record.
2. Read-only verification for each token against the installed Coolify:
   - `GET /api/v1/version` returns 4.4.7;
   - `GET /api/v1/team` returns the expected team;
   - `GET /api/v1/projects` and the approved application read succeed;
   - no 401/403.
3. Prove write/deploy ability only on a disposable Stage A test application:
   - `vula-m4-staging` is used by the staging CP to create and deploy
     `za-pos-m4-store-a` (Stage A itself);
   - `legacy-cp-replacement` may trigger one deployment of that disposable test
     app, then be verified as terminal and healthy. This does not touch OptiMed
     or any existing tenant.
4. If write/deploy verification fails, stop; do not update consumers or revoke
   the old token.

### Phase 2 — update Vula consumers

1. Update the Vula Control Plane staging/production app environments and local
   `.env` files with the replacement through the approved secret path.
2. Restart the Vula Control Plane container(s) so the new environment is read.
3. Verify `/health`, office login, `/api/releases` read, and a read-only Coolify
   probe using the new token.
4. Do not deploy existing tenants as part of the token test.

### Phase 3 — update OptiMed, with separate approval

This phase is **not** part of Vula M4.1 and must not start without explicit
OptiMed approval.

1. Update only the OptiMed Control Plane's `COOLIFY_API_TOKEN` environment
   (and its `.env` if that is the deployment source).
2. Restart only the OptiMed Control Plane, not practice apps, the panel app,
   volumes or databases.
3. Verify:
   - `optimed-control-plane` status is healthy;
   - `https://omcp-mzsza-2026.optimed-app.co.za/health` 200;
   - a read-only platform view works with the new token;
   - no OptiMed practice app, domain, volume or database changed.
4. If any check fails, restore the old token immediately under the rollback
   procedure and stop. Do not retry destructive actions.

### Phase 4 — revoke the exposed token

Only after Phase 2 and Phase 3 (if OptiMed is in scope) pass:

1. Revoke the exposed old token in Coolify.
2. Verify both control planes still perform a read-only Coolify probe.
3. Verify OptiMed health endpoints remain unchanged.
4. Record the revocation time and token ID (not the value) in the audit log.
5. Keep the new token IDs/owners recorded; never write token values to disk
   outside the approved secret store.

## 5. Which services fail if the old token is revoked

| Service | Failure mode | Impact on running tenants |
| --- | --- | --- |
| Vula Control Plane | Coolify API 401/403; provisioning, redeploy, release/rollback/waves fail | Existing stores keep selling; their DBs and health are unaffected |
| Vula release script | deploy request fails | No tenant app is stopped by the script; no deployment starts |
| OptiMed Control Plane | platform create/deploy/restart/stop/start/domain/teardown fails | Existing practice/panel apps keep running; no automatic stop |
| Coolify probes | report unauthenticated | Monitoring/reporting only |

No running tenant application is stopped merely by revoking the API token. The
failure is control-plane operations, not tenant runtime.

## 6. Rollback and recovery

1. **Before revocation:** the old token remains valid. If a consumer fails,
   restore that consumer's previous environment and restart only that control
   plane. Verify health and the read-only probe. This is the preferred rollback.
2. **Keep a pre-created fallback token** (`legacy-cp-fallback`) if the old token
   must be revoked before every consumer is verified. Update a failed consumer
   to the fallback, verify, then revoke the fallback when stable. Do not create
   fallback tokens containing root or sensitive abilities.
3. **After revocation:** if the replacement fails, do not revive the exposed
   token. Use the fallback token and re-run the read-only probe and health
   checks. If the failure is wider than one consumer, stop and report; do not
   make broad Coolify changes.
4. **OptiMed:** never restart or redeploy an OptiMed practice app to recover from
   a token problem. Only the OptiMed Control Plane environment/restart is in
   scope, and only with separate approval.
5. **No secret recovery by printing:** never read a token back from Coolify or a
   database into logs, reports, shell history or chat. If a value is lost,
   create a new token and repeat the update; do not attempt to recover the old
   value.

## 7. Open blockers

- The existing exposed token cannot be revoked until Vula and OptiMed are
  coordinated. OptiMed restart approval is a prerequisite.
- Deployed app env values are masked; the exact old value in each CP app cannot
  be proven read-only. Treat both as consumers.
- Coolify 4.4.7 has no project/app token scope; both replacement tokens remain
  Root Team-wide. Rotation reduces the exposure window, not the underlying
  permission breadth.
- This plan does not rotate any credential by itself.
