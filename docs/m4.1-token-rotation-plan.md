# M4.1 Coolify Token Rotation Plan

**Status:** executed 2026-10-23. Four per-application tokens were created; OptiMed,
Vula production and existing Vula staging Control Planes were updated and
verified; the exposed token was revoked and confirmed 401. OptiMed practice
applications were not modified. Execution details:
[`docs/m4.1-stage-a-execution.md`](./m4.1-stage-a-execution.md).

The rotation is **independent of Stage A**. It did not create, deploy or require
the M4 staging Store. Stage A also did not wait for this rotation; its Control
Plane got its own token. The only shared prerequisite is that neither flow uses
the exposed token.

## 1. Why the old token must be replaced

The exposed Root Team Coolify API token is used by multiple applications:

| Consumer | Evidence | What breaks without a valid token |
| --- | --- | --- |
| Vula production Control Plane | `/home/hoosain/apps/za-pos-control-plane/.env` contains the exact exposed value; `src/services/coolify.ts` reads `COOLIFY_API_TOKEN` | Provisioning, redeploy, release apply/rollback and waves |
| Vula existing staging Control Plane | Coolify app `vula-cp-staging` exposes a `COOLIFY_API_TOKEN` env key (value masked by the API) | Its Coolify-backed lifecycle actions |
| OptiMed Control Plane | `/home/hoosain/apps/optimed-control-plane/.env` contains the exact exposed value; `src/services/coolify.ts` reads `COOLIFY_API_TOKEN` | Practice provisioning, deploy, restart, stop/start, domain reassignment and teardown |
| OptiMed deployed Control Plane | Coolify app `optimed-control-plane` exposes a `COOLIFY_API_TOKEN` env key (value masked by the API) | Same OptiMed platform operations |
| Vula release script | `za-pos-control-plane/scripts/release-apps.sh` now reads only its own repository-root `.env` or its own environment | `release-apps.sh fleet/cp/all/<name>` cannot deploy |
| Coolify probes | Each control plane's `scripts/coolify-probe.ts` | Its own connectivity check reports failure |

The audit searched the entire `/home/hoosain/apps` tree, shell history,
user/system systemd units and cron. Only the Vula and OptiMed Control Plane
`.env` files contained the exact exposed value. No local running process, local
Docker container, cron entry or systemd unit contains it. No CI workflow file
references it. Deployed app env values are masked, so both deployed Control
Planes are treated as consumers even though their exact current value cannot be
proven read-only.

## 2. Per-application credential design

There is **no shared replacement token**. Each application gets its own
credential, with the minimum supported abilities. Under Coolify 4.4.7 every token
is still **Root Team-scoped**; this separation reduces blast radius and makes
rotation independent, not Coolify permission scope.

| Consumer | Dedicated token name | Abilities |
| --- | --- | --- |
| OptiMed Control Plane | `coolify-optimed-cp` | `read`, `write`, `deploy` |
| Vula production Control Plane | `coolify-vula-prod-cp` | `read`, `write`, `deploy` |
| Existing Vula staging Control Plane | `coolify-vula-staging-cp` | `read`, `write`, `deploy` |
| New Vula M4 staging Control Plane | `coolify-vula-m4-staging-cp` | `read`, `write`, `deploy` |

No token receives `root`, `read:sensitive` or `write:sensitive`. Each token is
stored only in its own application's environment/secret store and read only by
that application. The Vula release script uses only the Vula Control Plane's own
`.env` or its own environment; it no longer falls back to OptiMed and fails closed
if its own credential is missing.

The M4 token is created and verified during this rotation but is not used until a
separately approved Stage A. Creating it does not require an M4 application.

## 3. Verification without Stage A

Each token is verified independently, before any consumer is switched:

1. **Authentication/read verification:** `GET /api/v1/version`, `/team`,
   `/projects`, `/servers` and the relevant application read return 200, not
   401/403.
2. **Write/deploy capability probe without mutation:** use a deliberately
   invalid write request that fails validation before any resource is created.
   For example, `POST /api/v1/applications/dockerimage` with an empty body must
   return a validation error, not 401/403; `POST /api/v1/deploy?uuid=<non-existent
   uuid>&force=false` must return not-found/validation, not 401/403. Record the
   status and verify no application/deployment count changed. Do not send a
   valid create/deploy request.
3. **Control Plane operation:** after a consumer is switched, verify its
   `/health`, office login, and a read-only application view. For OptiMed, use
   read-only platform/Coolify metadata only. For Vula, use a read-only releases/
   fleet view. Do not deploy a tenant or practice app as a token test.
4. **No Stage A dependency:** no test requires `za-pos-m4-store-a`, the staging
   CP, release A or a Stage A volume.

## 4. Coordinated rotation sequence

This sequence requires separate approval. Nothing below is executed by the
current repository-side preparation.

### Phase 0 — freeze and baseline

1. Record current Vula and OptiMed health, Coolify app statuses, token IDs,
   consumer list and the no-deployment state. Never record token values.
2. Confirm no Coolify deployment is queued or running, and no release wave is
   active.
3. Record OptiMed health/Coolify metadata baseline before touching its CP.
4. Keep the exposed old token valid until Phase 5 completes.

### Phase 1 — create and independently verify four tokens

1. Create `coolify-optimed-cp`, `coolify-vula-prod-cp`,
   `coolify-vula-staging-cp` and `coolify-vula-m4-staging-cp` with the abilities
   in §2 and a bounded expiry. Record token IDs, owner, abilities and expiry.
2. Run the read-only and negative-write probes from §3 for each token.
3. Confirm no Coolify application/deployment count changed.
4. If any token fails authentication or the negative write probe, stop. Do not
   update any consumer and do not revoke the old token.

### Phase 2 — OptiMed Control Plane, separately approved window

OptiMed is a separate application and remains out of Vula M4.1 scope.

1. With explicit OptiMed approval, set only the OptiMed Control Plane's
   `COOLIFY_API_TOKEN` to `coolify-optimed-cp`.
2. Restart **only** the OptiMed Control Plane container. Do not restart, redeploy,
   stop, modify or delete any OptiMed practice app, panel app, database, volume or
   domain.
3. Verify:
   - `optimed-control-plane` status healthy;
   - `https://omcp-mzsza-2026.optimed-app.co.za/health` 200;
   - read-only Coolify API metadata works with the new token;
   - all previously healthy OptiMed practice endpoints remain healthy.
4. If anything fails, restore the old token only in the OptiMed Control Plane,
   restart only that CP, verify health, and stop the rotation.

### Phase 3 — Vula production Control Plane

1. Set only the Vula production Control Plane's token to
   `coolify-vula-prod-cp`.
2. Restart that Control Plane only.
3. Verify `/health`, office login and a read-only releases/fleet view. Do not
   deploy a tenant.
4. If it fails, restore its old token and restart only that CP.

### Phase 4 — existing Vula staging Control Plane

1. Set only `vula-cp-staging`'s token to `coolify-vula-staging-cp`.
2. Restart that Control Plane only; verify health/login/read-only view.
3. Do not touch tenant apps.
4. M4 staging is separate: `coolify-vula-m4-staging-cp` is already verified but
   is not used until Stage A is separately approved.

### Phase 5 — revoke the exposed token

Only after OptiMed (if in scope), Vula production and existing Vula staging are
updated and verified:

1. Confirm no consumer still references the old token. The old token remains
   valid until this point.
2. Revoke the exposed token in Coolify.
3. Confirm the old token **no longer authenticates**: a `GET /api/v1/version`
   with it returns 401. Do not print the token or response headers.
4. Verify each new token still returns 200 on `/version` and each Control Plane
   remains healthy.
5. Recheck OptiMed health endpoints and confirm they are unchanged.
6. Record revocation time, token ID and verification results; never token values.

If OptiMed's separate window is delayed, Vula may complete Phases 3–4, but the
old token stays valid and the rotation is not complete. Do not revoke it while
OptiMed still depends on it.

## 5. Failure impact after separation

| Revoked/failed credential | Failing service | Running deployments |
| --- | --- | --- |
| `coolify-optimed-cp` | OptiMed platform lifecycle operations only | OptiMed practice and panel apps keep running; no automatic stop |
| `coolify-vula-prod-cp` | Vula production CP provisioning/redeploy/releases | Existing stores keep selling; DBs/health unaffected |
| `coolify-vula-staging-cp` | Existing Vula staging CP Coolify operations | Existing staging tenants unaffected |
| `coolify-vula-m4-staging-cp` | M4 staging CP only, once Stage A exists | No production/demo tenant impact |

Revoking an API token does not stop a running tenant application. The failure is
control-plane administration, not tenant runtime.

## 6. Rollback/recovery

1. **Before Phase 5:** the exposed old token is still valid. If one consumer
   fails, restore the old token only in that consumer's environment and restart
   only that Control Plane. Do not touch other applications.
2. **OptiMed failure:** restore its old token and restart only the OptiMed
   Control Plane. Never restart a practice app or change a practice database/
   volume/domain to recover a credential.
3. **After revocation:** do not revive the exposed token. Create a new
   per-application token, update only the failed consumer, verify with the §3
   probes and health checks, then revoke the failed replacement.
4. **No shared fallback:** do not reintroduce a shared token or a cross-app
   `.env` fallback. Each application must recover with its own credential.
5. **Token values:** never read a token back into logs/reports/history. If a
   value is lost, create a new per-app token and repeat the update.

## 7. Open blockers

- OptiMed Control Plane restart requires a separately approved
  credential-maintenance window. Its practice apps, databases, volumes, domains
  and deployments remain untouched.
- Deployed Control Plane env values are masked; exact old-value equality cannot
  be proven read-only. Treat all four Control Plane rows as consumers.
- Coolify 4.4.7 has no project/app token scope. Four dedicated tokens reduce
  blast radius but remain Root Team-wide.
- The exposed token remains valid until Phase 5; no Stage A dependency requires
  it.
